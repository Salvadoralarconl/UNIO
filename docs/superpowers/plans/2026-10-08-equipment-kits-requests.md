# Equipment Kits and Requests — approved visual implementation
User approved Kits/Requests concept render and prioritizes these two. Retain Brie icon rail, warm background, rounded white workspace, custom dropdowns, aligned controls, monochrome summary cards and restrained state colors. Status/Reports remain separate. No public/cloud deployment; existing local5174 backend5081. Preserve company isolation, immutable audit, sessions, capabilities, actual data. No Git metadata; source snapshots retained.

Kits: company-owned reusable templates with name, optional active departmentID (null all), active flag, revision, equipment lines (one of five asset types, optional custom category, quantity1–100); normalized duplicate lines rejected. List/search, view/edit/create and computed stock availability. No deletion required; archive via active flag, uses existing Write permission.
Requests: title, active employeeID, optional active departmentID, kitID, needed date, notes, persisted ticketID, revision. Snapshot kit lines at creation so edits cannot alter old requests. States Pending -> Approved -> Ready -> Completed, Pending/Approved -> Cancelled. Create is Write; Approve/Assign/Complete requires Approve. Viewer read-only company scope; AssignedOnly cannot enumerate kits/requests/tickets. Approve and assign is atomic: company/user/session authority revalidated, stable locks, all required Available assets unassigned selected deterministically by ID, matching type and optional normalized category; updates asset employee/department/status/revision, immutable audits and inventory_activity in same transaction. Insufficient stock409, no partial assignment. Repeating/stale actions409. No automatic reassignment/release on Cancelled; only unassigned states cancellable. Employee membership IDs are directory identities, not login userIDs.
Tickets: minimum genuine company-owned equipment ticket stored with request and synchronized state, immutable IDs, no third-party integration claim. Requests show real linked ticket detail via endpoint/dialog. New onboarding request can opt into immediate assignment when authorized; otherwise Pending. Insufficient stock rolls back immediate creation with actionable error; user can save Pending instead. Full Tickets module roadmap remains separate.

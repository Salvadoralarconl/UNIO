# Operator and company account management design

Date: 2026-10-08
Status: approved by user2026-10-08; supersedes earlier company role and membership administration requirements. Existing inventory, directory and data preservation requirements remain.

## Intent and existing application
The platform owner alone manages companies, subscriptions and their Administrator assignment. Each company manages its Editors and Viewers within purchased seats. Existing sign-in uses secure HttpOnly cookie sessions and OIDC, with an explicit loopback-only development identity. CompanyAccess resolves active user, company and membership from the database on protected requests. Company-owned repositories and file serving are already scoped; immutable inventory audit and optimistic revisions exist. Current roles Admin/Technician/Manager/Employee, multi-company memberships and unrestricted Admin membership assignment conflict with this design and must be replaced. No foundation migrations have yet been applied to the actual lab database.

## Sole Operator
Use a singleton database ownership record constrained to one fixed key, referencing exactly one verified users identity. Bootstrap through a local administrative command; no public registration, promotion or Operator assignment endpoint. The Operator is a platform capability, not a company membership role. Bind through validated issuer and subject, never an email comparison or client claim. Revalidate the active owner on every Operator API request. All /api/operator operations require this capability, antiforgery for mutations, and no company context bypass for ordinary application APIs. Local identity selection requires the user's answer; until configured, Operator operations fail closed. Production uses the selected provider's verified stable identity.

Dedicated Operator page lists companies and opens company details: name/status, plan and limit, enabled accounts, invitations, seat usage/remaining, over-limit warning, online count and last activity. Company details list users and account status, role and last activity; owner can suspend/reactivate company and users, create/replace Administrator and edit subscription. Use website's off-white shell, white rounded panels, thin neutral borders, outline icons, black primary actions and existing custom dropdowns. Login uses separately approved light split panel with soft warm gradient.

## Company identity and roles
A non-Operator user belongs to one company, enforced in storage and backend. Existing multi-company memberships, if any, must be reported by migration rehearsal and explicitly resolved rather than silently reassigned. Existing Admin maps to Administrator, Technician to Editor, Manager to Viewer. Legacy Employee maps to Viewer with its existing own-assigned-inventory visibility restriction retained as an explicit scope. Do not broaden access during migration. Existing company data, IDs, files and history remain.

Administrator is assigned only by Operator. Administrators create/invite only Editor or Viewer, change only those users' roles and enablement, and see company seats. They cannot change themselves, another Administrator, company ownership, subscription or company association. Operator replaces an Administrator transactionally; replacing does not silently delete old user or data. Exactly one enabled Administrator per active company is the default invariant; creation of a company and its initial Administrator is atomic. Operator can suspend a company or disable its Administrator, exposing a needs-administrator state until repaired. Reactivating a company does not silently reactivate disabled accounts.

Editor may read/create/edit permitted company content. Deletion is a separate backend capability, denied to Editor by default. Administrator may delete within existing application rules. Viewer is read-only: no create/edit/delete/approve/index/repair/settings writes. Classify every endpoint by actual effect, including POST actions and routes currently grouped as Knowledge. Viewer AI/chat writes are denied under the strict read-only requirement. Scope restrictions are separate from role.

## Plans, seats and concurrency
Plan kinds: 10,20,50,100,Custom,Unlimited. Custom requires integer greater than100; Unlimited stores no numeric cap and remains a distinct kind. Operator alone changes plan. Enabled company accounts including Administrator consume seats. Disabled accounts do not. Pending, unexpired, unrevoked invitations reserve seats. Seat usage = enabled accounts + pending reserved invitations. Remaining = max(0,limit-usage), or unlimited. Over-limit = usage>limit; reducing a limit preserves all accounts/invitations and blocks net new seats.

All account creation, invitation issuance/acceptance/reactivation and subscription changes take the same company row lock in a transaction and recompute usage. Invitation acceptance converts one reservation to one enabled account atomically; duplicate/replayed acceptance cannot double count. Updates that do not add a seat remain allowed when over limit. Enabling an account requires capacity. Return a clear conflict response and current usage/limit. Company suspension blocks company operations; only Operator can manage suspended companies. Do not repurpose active/inactive directory employees as login account seats.

## Invitations and provisioning
Reuse existing trusted provider identity for accounts. Direct creation binds a verified provider issuer/subject supplied by authorized provisioning, without inventing local passwords. Invitations carry company, Editor/Viewer role, normalized intended email, expiry and hashed random single-use token. Acceptance requires authenticated provider identity with verified matching email, or an explicitly bound issuer/subject; never trust request email. Default invitation expiry seven days. Expired/revoked invitations release seats. Revocation is auditable. Reissue replaces the reservation atomically. No token is stored in plaintext or written to audit/logs.

No email delivery integration exists in the inspected identity subsystem. Initial delivery recommendation: show an authorized, copyable invitation link once for manual sharing; do not claim an email was sent. Automated email can use a configured provider later. User may select email delivery before this design is finalized.

## Presence and revocation
Enabled is permission status, not online status. Persist authenticated activity per session, with throttled heartbeat while app is visible; online means a non-expired session with activity within five minutes. Count distinct users, not sessions. Last activity is the most recent authenticated activity. Explicit logout revokes its session; disabled users and suspended companies cannot refresh presence. Presence never authorizes access. Revalidate account/company/session status for every protected request so existing sessions lose access on next request; abort/clear frontend company state on denial. Do not promise cancellation of an operation already committed before revocation.

## Audit and safeguards
Append immutable platform/company audit entries in the same transaction for company create/edit/suspend/reactivate, subscription changes, Administrator assignment, user creation/role/status changes and invitation lifecycle. Include actor, company/resource, before/after and timestamp, never secrets/tokens. Platform audit readable only by Operator; company audit limited to own company Administrator. Expected revisions prevent stale operator/admin edits. Use request-specific trusted access contexts, never client-supplied company IDs as authority.

## Verification and preservation
Add negative backend tests for every role; non-Operator cannot reach platform routes, forge promotion or change subscription; Administrator cannot create Administrator or mutate self/foreign users; Viewer cannot mutate; Editor cannot delete by edit privilege. Parallel last-seat tests for invite/create/reactivate/acceptance, expiry and over-limit reductions. Test disabled accounts/suspended companies with existing sessions, cross-company IDs/files/history, invitation replay and identity mismatch, presence counts and audit transaction rollback.

Rehearse numbered migrations against an isolated restored database and copied files before real lab changes. Verify record IDs/counts/relationships/file links. Back up actual lab database/files before rollout. Continue existing authentication transport verification for localhost port5174; no weakening secure cookies or production OIDC. Run backend suite, frontend build, isolated browser tests, desktop/mobile visual checks and independent review before reporting ready. No synthetic records in real user inventory.
